# HSL25 — StarLine Hackathon 2025 (очный этап)

Подготовка команды (6 человек) к очному этапу робототехнического хакатона
StarLine 2025 (в рамках РобоФиниста). Задача — создать цифровой двойник
предоставляемого робота, т.к. организаторы его не дают (как и в прошлом году).

## Структура рабочего пространства

- `hsl25-master/` — официальный репозиторий организаторов (не git, распакованный
  архив). Ключевое:
  - `kobuki/workspace/src/kobuki_ros/kobuki_description/` — URDF/меши базы kobuki
    (уже включает `kobuki_gazebo.urdf.xacro` с рабочими Gazebo Classic плагинами:
    diff drive, IMU/gyro, бампер, cliff-сенсоры — **основа для двойника, уже готова**)
  - `kobuki/workspace/src/livox_ros_driver2/` — реальный драйвер лидара (не для
    симуляции, общается с физическим сенсором по сети)
  - `kobuki/docker/` — Dockerfile на базе `nickodema/kobuki:humble-22.04-100625`
    (ROS2 Humble, Ubuntu 22.04). На реальном роботе всё запускается **только
    из этого контейнера** (`build.bash`/`run.bash`/`into.bash`/`stop.bash`),
    `kobuki/workspace` монтируется внутрь.
  - `docs/Очный - HSL25 v021025.pdf` — регламент очного этапа (см. ниже конспект)
- ⚠️ **`hackaton/` помечена `COLCON_IGNORE`** (файл `~/ros2_ws/src/hackaton/COLCON_IGNORE`,
  пустой маркер) — иначе colcon рекурсивно находит внутри `hsl25-master`
  пакеты с именами, которые нужны нам в других, "облегчённых" версиях (см.
  `livox_ros_driver2` ниже), и падает на `Duplicate package names not
  supported`. Маркер безопасен: docker-сборка реального робота — это
  ОТДЕЛЬНЫЙ вызов colcon с base-path `kobuki/workspace` внутри контейнера,
  файла из `~/ros2_ws/src/hackaton/` он не видит и не может увидеть.
  Пакеты, нужные из `hackaton/`, забираются наружу поштучно (симлинком —
  `kobuki_ros_interfaces`, или отдельной облегчённой копией —
  `livox_ros_driver2`), а не сборкой `hackaton/` целиком
- `~/ros2_ws/src/hsl_description/` (**вне** папки `hackaton/`, соседний пакет
  в основном workspace) — рабочая копия URDF/меши kobuki, вынесенная из
  `hsl25-master/kobuki/workspace/src/kobuki_ros/kobuki_description` в отдельный
  чистый ROS2-пакет для удобной разработки двойника (в оригинале слишком много
  вложенных не относящихся к делу папок). Все ссылки (`$(find ...)`,
  `package://...`) переименованы `kobuki_description` → `hsl_description`,
  собран и проверен (`colcon build --packages-select hsl_description --symlink-install` +
  `ros2 launch hsl_description robot_description.launch.py` — модель грузится
  в RViz штатно, без обходных трюков; `--symlink-install` обязателен, иначе
  правки в `urdf/*.xacro` не подхватываются без пересборки). База kobuki (10
  линков) плюс надстройка в `urdf/mast.urdf.xacro` (4 стойки + `platform_link`
  + `lidar_mount_link` с полным сенсорным стеком Livox MID-360 — IMU и сам
  лидар, см. ниже), собираются вместе в `urdf/hsl_robot.urdf.xacro`
  (файл-выбор модели — launch-аргумент `urdf_file`, дефолт остался
  `kobuki_standalone.urdf.xacro`, т.е. голая база). Gazebo-плагины см.
  отдельный раздел ниже. Тестовый запуск в Gazebo:
  `ros2 launch hsl_description gazebo.launch.py` (см. также ⚠️-нюансы
  Gazebo-окружения в соответствующем разделе — без них либо не видно
  мешей корпуса/колёс, либо не видно пола/света). По умолчанию поднимает
  и RViz (`rviz/gazebo.rviz` — RobotModel + TF + `PointCloud2` на
  `livox/lidar` с Color Transformer=Intensity, Fixed Frame=`odom`,
  `Decay Time: 3` (визуальное накопление за последние 3с — каждое
  сообщение `livox/lidar` само по себе содержит только ТЕКУЩИЙ скан, как
  и реальный робот, накопление истории — чисто настройка отображения в
  RViz, данные не меняются); выключить RViz: `rviz:=false`)
- `hsl_description/data/rosbag2_2026_06_27-*` — реальные bag-записи (mcap)
  с этапа квалификации: `/livox/lidar`, `/livox/imu`, `/tf_static`.
  Читать: `rosbag2_py` + `rclpy.serialization.deserialize_message`
  (`storage_id='mcap'`) — полезный референс для сверки формата/плотности/
  распределения intensity с симуляцией, уже пригодилось при подборе
  `lidar_samples` (см. секцию «Симуляция лидара»)
- `~/ros2_ws/src/kobuki_ros_interfaces` — **реальная копия** (не симлинк —
  изначально был симлинк на `hsl25-master/kobuki/workspace/src/
  kobuki_ros_interfaces`, но при передаче пакета товарищам по команде
  симлинк на файл ВНЕ `hsl_description` был бы битым без всей папки
  `hackaton/` в точности той же относительной структуры; заменили на
  `cp -rL`, т.к. это чистый message-only пакет без докер-специфичных
  зависимостей — копировать безопасно, в отличие от `livox_ros_driver2`
  ниже). Нужен, чтобы `hsl_description` мог публиковать
  `kobuki_ros_interfaces/msg/SensorState` в симуляции тем же типом,
  что и реальный `kobuki_node`. Собирается отдельно:
  `colcon build --packages-select kobuki_ros_interfaces`
- `~/ros2_ws/src/livox_ros_driver2` — **НЕ симлинк и НЕ копия** реального
  `hackaton/hsl25-master/.../livox_ros_driver2` (тот трогать нельзя — он
  монтируется в докер-контейнер реального робота). Это отдельный, специально
  созданный пакет с тем же именем, содержащий ТОЛЬКО `msg/CustomPoint.msg` +
  `msg/CustomMsg.msg` (текст скопирован 1-в-1, без переименования). Причина:
  полная сборка настоящего `livox_ros_driver2` требует
  `liblivox_lidar_sdk_shared.so` (реальный Livox SDK под `/usr/local/lib`,
  которого на машине разработки нет и не должно быть — SDK для связи с
  физическим железом), `find_library(...REQUIRED)` у него в CMakeLists.txt
  аварийно останавливает конфигурацию ДО генерации даже самих сообщений.
  А `ros2_livox_simulation` (ниже) на этапе компиляции просит
  `find_package(livox_ros_driver2 REQUIRED)` и
  `#include <livox_ros_driver2/msg/custom_msg.hpp>` только ради самого типа.
  Имя пакета совпадает с настоящим намеренно — иначе пришлось бы патчить
  исходники `ros2_livox_simulation`. Подробности — в `package.xml` этого
  пакета
- `~/ros2_ws/src/ros2_livox_simulation` — **перенесён** сюда из
  `hsl_description/livox_laser_simulation_ros2-main/` (там он оказался как
  вложенный ROS2-пакет внутри другого пакета — рабочает, но нестандартно и
  провоцирует конфликты имён с colcon; перенос в отдельный sibling-пакет —
  правильное место). Патчи в `CMakeLists.txt` и `src/livox_points_plugin.cpp`
  — см. секцию «Симуляция лидара» ниже, там же зафиксированы все находки по
  несовместимостям этого форка с текущим окружением
- `starline-hackathon-2020-2-stimulator_g/` — решение другой команды с хакатона
  2020 года. **Не переиспользуется**: ROS1/catkin (не ROS2), другие сенсоры
  (Astra RGBD + RPLidar A2, 2D-лидар — не Livox), другой сценарий (навигация
  по "городу" S→F, а не лабиринт с маркерами), другой навстек (move_base/gmapping,
  не Nav2). Ценность только историческая/справочная.

## Передача пакета команде — что копировать

Просто `hsl_description/` **недостаточно** — цифровой двойник собирается из
**4 пакетов**, три из которых лежат СНАРУЖИ этой папки, плюс отдельный шаг
настройки workspace:

1. `~/ros2_ws/src/hsl_description/` — основной пакет
2. `~/ros2_ws/src/ros2_livox_simulation/` — Gazebo-плагин лидара (патченый форк)
3. `~/ros2_ws/src/livox_ros_driver2/` — пакет-заглушка только с двумя типами
   сообщений (см. описание ниже) — **НЕ** то же самое, что настоящий
   `livox_ros_driver2` из `hsl25-master`
4. `~/ros2_ws/src/kobuki_ros_interfaces/` — реальная копия (не симлинк)
   сообщения `SensorState` и других

Все 4 — обычные папки без внешних ссылок, копируются как есть (`cp -r`,
архив, git — что угодно). Дальше на машине товарища:

```bash
# системные зависимости (Ubuntu 22.04 + ROS2 Humble уже должны быть)
sudo apt install ros-humble-gazebo-ros-pkgs ros-humble-gazebo-ros \
    ros-humble-gazebo-plugins python3-numpy

source /opt/ros/humble/setup.bash
colcon build --packages-select kobuki_ros_interfaces livox_ros_driver2 \
    ros2_livox_simulation hsl_description --symlink-install
source install/setup.bash
source src/hsl_description/setup_env.sh   # ОБЯЗАТЕЛЕН перед gazebo.launch.py —
                                            # без него gzserver либо зависает
                                            # на 20-30с, либо без пола/света
ros2 launch hsl_description gazebo.launch.py
```

⚠️ Если у товарища в workspace ТОЖЕ будет лежать `hackaton/hsl25-master`
(например, он скачает официальный архив организаторов отдельно) —
положить рядом файл `hackaton/COLCON_IGNORE` (пустой), иначе colcon
найдёт внутри пакет `livox_ros_driver2` с тем же именем, что и наша
заглушка, и упадёт на `Duplicate package names not supported` (см. ниже
подробное объяснение в структуре workspace).

`setup_env.sh` — новый файл, оформляет то, что раньше было только текстом
в этом CLAUDE.md (`export GAZEBO_MODEL_DATABASE_URI=""` +
`source /usr/share/gazebo/setup.sh`, именно в этом порядке — иначе
`gazebo/setup.sh` сам перезатирает `GAZEBO_MODEL_DATABASE_URI` обратно на
онлайн-адрес, проверено вживую).

## Целевая среда

- **ROS2 Humble**, Ubuntu 22.04 (задано Dockerfile'ом организаторов)
- **Gazebo 11 Classic** (не Ignition/новый Gazebo) — выбран, т.к. под него есть
  готовые плагины и для kobuki (уже в репозитории), и для Livox MID-360
  (community-форки). На машине разработки уже стоит Ignition Fortress — это не
  мешает, `gazebo`/`gazebo_ros_pkgs`/`gazebo_dev`/`gazebo_plugins` ставятся из
  тех же apt-репозиториев без конфликта (разные бинарники: `gazebo`/`gzserver`
  vs `ign`/`gz`)
- Языки: **Python (rclpy)** для всей командной логики (детекция, валидация
  маркеров, стратегия, интеграция) — низкий порог входа для новичков в команде.
  C++ трогать не планируется, кроме точечных патчей стороннего Gazebo-плагина
  лидара при необходимости

## Gazebo 11 Classic — установлено и проверено

`sudo apt install ros-humble-gazebo-ros-pkgs ros-humble-gazebo-ros ros-humble-gazebo-plugins`
(из Ubuntu jammy universe, без сторонних PPA — `gazebo11-gz-cli` не нужна:
на машине стоит Ignition **Fortress**, а не Garden/Harmonic, у него CLI `ign`,
не `gz`, конфликта файлов с classic-Gazebo нет и не будет).

Установка проверена вживую: `gzserver`/`gzclient` 11.10.2+dfsg-1, ROS2-мост
(`gazebo_dev`, `gazebo_msgs`, `gazebo_plugins`, `gazebo_ros`,
`gazebo_ros_pkgs`) виден через `ros2 pkg list`, сервисы `/spawn_entity`,
`/delete_entity` и топик `/clock` подтверждены рабочими.

⚠️ **Известный нюанс (не баг)**: при каждом старте `gzserver` синхронно
пытается достучаться до онлайн-базы моделей `models.gazebosim.org`, из-за
чего полная инициализация (появление `/spawn_entity` и т.п.) может
затягиваться на 20-30+ секунд и выглядеть как зависание. Обход — отключить
онлайн-базу (она всё равно не нужна, все модели свои):

```bash
export GAZEBO_MODEL_DATABASE_URI=""
```

Стоит прописать это в `~/.bashrc` каждого участника команды (или в
Dockerfile/launch-скриптах проекта), иначе новички в команде решат, что
Gazebo сломался, хотя он просто ждёт сетевой таймаут.

⚠️ **Ещё один нюанс окружения**: одного `source /opt/ros/humble/setup.bash` +
`source install/setup.bash` **недостаточно** для `gzserver` — без
`GAZEBO_MODEL_PATH`/`GAZEBO_RESOURCE_PATH` он не находит даже встроенные
`model://ground_plane` и `model://sun` (которые использует дефолтный
`empty.world` из `gazebo_ros`), сыпет `Unable to find uri[...]` в лог, но
не падает — просто нет пола и света. Нужно ещё:

```bash
source /usr/share/gazebo/setup.sh
```

(проверено вживую: без этой строки — ошибки `Unable to find uri`, с ней —
чисто). Тоже стоит вынести в `~/.bashrc`/launch-обвязку, вместе со строкой
про `GAZEBO_MODEL_DATABASE_URI` выше.

⚠️ **На стороне отладки**: если `gzserver` падает сразу с `exit code 255`
без вообще какого-либо сообщения в стандартный лог launch — это почти
наверняка не баг плагина, а порт `11345` уже занят зависшим процессом
`gzserver` с прошлого неудачного запуска (`ros2 launch`/`Ctrl+C` не всегда
убивают его подпроцессы). Проверить: `ss -tlnp | grep 11345` — и `kill -9`
всё, что там висит, включая старые `spawn_entity.py`/`ros2 launch`.
Диагностируется однозначно через `gzserver --verbose ...` напрямую — он,
в отличие от launch-обвязки, печатает реальную причину (`Address already
in use`).

⚠️ **Меши не видны в Gazebo, хотя примитивы (box/cylinder) видны** — не баг
мешей, а отсутствующий экспорт в `package.xml`. `GAZEBO_MODEL_PATH`
собирается launch-обвязкой `gazebo_ros` (`GazeboRosPaths.get_paths()`)
только из пакетов, у которых явно прописано:

```xml
<export>
  <gazebo_ros gazebo_model_path="${prefix}/.."/>
</export>
```

Без этого `package://hsl_description/meshes/...` не резолвится, и Gazebo
молча не рисует mesh-геометрию (примитивы рендерятся без внешних файлов,
поэтому видны всегда, это и сбивает с толку). Уже добавлено в
`hsl_description/package.xml` — если заводить новый пакет с мешами
(например, для поля/маркеров), про этот экспорт не забыть сразу.

## Робот и сенсоры (жёстко зафиксированы регламентом)

Turtlebot2 (kobuki) + Livox MID-360 на кастомной мачте с NUC + Mikrotik.
**Регламент прямо запрещает добавлять любую сенсорику/сетевое железо/апгрейд
ПК** — набор сенсоров ниже это всё, что будет доступно на соревновании.

- **Livox MID-360**: 3D LiDAR, FOV 360°×59°, неповторяющийся паттерн сканирования.
  Реальный driver (`mid360.launch.py` + `MID360_tb_config.json`) публикует:
  - `livox/lidar` — `sensor_msgs/PointCloud2` (т.к. `xfer_format=0` в конфиге;
    поля x,y,z,intensity,tag,line), `frame_id="livox"`
  - `livox/imu` — `sensor_msgs/Imu`
  - статический TF `base_link → livox`: `xyz=(0,0,0.3) rpy=(π/2, π, 0)`
  - встроенный IMU — **ICM-40609** (6-осевой: гироскоп+акселерометр, БЕЗ
    магнитометра), 200 Гц
  - ⚠️ **`linear_acceleration` в единицах "g", не в м/с²** — драйвер не
    конвертирует ([issue #157](https://github.com/Livox-SDK/livox_ros_driver2/issues/157)).
    Для fusion-пакетов (robot_localization и т.п.) нужно домножать на 9.81
  - ⚠️ **`frame_id` у IMU-сообщения захардкожен как `"livox_frame"`**
    (`lddc.cpp:481`), а в TF-дереве фрейм называется `livox` — рассинхрон,
    ломает `tf2`-запросы, если не поправить
- **kobuki (база)**: свой отдельный 3-осевой гироскоп (`gyro_link`, физически
  ДРУГОЙ сенсор, не путать с Livox IMU) + энкодеры колёс (`left_encoder`/
  `right_encoder` в `SensorState.msg`) + бамперы + cliff-датчики (ИК, для
  этого полигона малополезны)
- Камеры на роботе нет вообще

## Симуляция лидара — готово, подключено к роботу, проверено вживую

`ros2_livox_simulation` (`~/ros2_ws/src/ros2_livox_simulation`, форк
`TGR-Robotics/livox_laser_simulation_ros2`, восходит к `LihanChen2004`).
Сенсорный блок (без собственного `<link>`/`<visual>` макроса
`urdf/mid360.xacro` — тот ссылается на `package://venice_robot_description/
meshes/mid-360-asm.stl`, которого у нас нет и не будет, чужой xacro писался
под другой проект) повешен прямо на уже существующий `lidar_mount_link`
(`urdf/mast.urdf.xacro`, уже правильно сориентирован под реальный static
TF — см. IMU-блок).

⚠️⚠️ **Прежде чем плагин вообще собрался, пришлось решить три независимые
проблемы** — типичная ситуация с форком стороннего кода, ничего не
заработало "из коробки":

1. **`CMakeLists.txt` требовал `epic_common`** (`find_package(epic_common
   REQUIRED)`) — пакета нет нигде в системе/workspace, не ROS2-пакет, похоже
   на внутреннюю библиотеку автора форка. Нашли, что используется ТОЛЬКО в
   отдельном `csv_main` (offline-утилита просмотра `scan_mode/*.csv`,
   никак не участвует в самом Gazebo-плагине) — `csv_main` целиком убран
   из сборки, `epic_common` тоже убран
2. **Захардкожены `libprotobuf.so.9` / `libboost_chrono.so.1.71.0`** —
   таких версий на Ubuntu 22.04 нет (реально стоит protobuf 23, boost
   1.74), линковка падала. Ни один `.cpp` плагина protobuf напрямую не
   использует (нужен транзитивно Gazebo transport через
   `${GAZEBO_LIBRARIES}`) — просто убран явный line. `boost::chrono`
   используется напрямую (Gazebo `transport::Node`) — переведён на
   нормальный CMake-таргет `Boost::chrono` вместо пути к конкретной `.so`
3. **`livox_points_plugin.cpp` писал в `CustomMsg` УСТАРЕВШЕЙ схемы**
   (плоские параллельные массивы `xs[]`/`ys[]`/`zs[]`/`offset_times[]`/
   `reflectivitys[]`/`tags[]`/`lines[]`/`frame_id[]`/`publish_time_ns`/
   `timebase_ns`) — так `CustomMsg.msg` выглядел в более старой версии
   `livox_ros_driver2`. У реального driver'а организаторов схема другая:
   `header` (стандартный `std_msgs/Header`) + `timebase` + `point_num` +
   `lidar_id` + `rsvd` + `CustomPoint[] points` (массив структур). Компилятор
   сразу на это указал (`has no member named ...`) — в закомментированном
   коде рядом уже лежала ПОЛОВИНА правильного перехода на новую схему
   (кто-то начал и бросил), патч закончил её: `header.stamp`/`header.frame_id`
   вместо `frame_id[]`/`publish_time_ns`, `timebase` вместо `timebase_ns`,
   `CustomPoint`-в-цикле + `points.push_back()` вместо записи по индексу в
   параллельные массивы

Топики (проверено живым тестом в Gazebo, не только компиляцией):
- Плагин публикует ОБА формата, но **не равноценно**: `<topic>` (у нас —
  скрытый `_raw/livox_lidar`) — `livox_ros_driver2/msg/CustomMsg`, честная
  reflectivity на точку (`rayShape->GetRetro(...)`, т.е. значение
  `<laser_retro>` из SDF); `<topic>_PointCloud2` (`_raw/livox_lidar_PointCloud2`,
  не используется) — конвертация БЕЗ intensity/reflectivity (теряется!)
- Т.к. детекция маркеров опирается на отражательную способность, а реальный
  робот публикует именно PointCloud2 с intensity (`xfer_format=0`) — вопрос
  "либо xfer_format=1 на реальном драйвере, либо писать конвертер" (раньше
  был открытым) **решён в пользу конвертера**: `scripts/livox_lidar_bridge.py`
  подписан на `_raw/livox_lidar` (CustomMsg), вручную собирает
  `sensor_msgs/PointCloud2` по ТОЧНО тому же байтовому макету, что и
  реальный `livox_ros_driver2` (сверено с исходником, не по памяти:
  `lddc.cpp::InitPointcloud2Msg` + `struct LivoxPointXyzrtlt` в `comm.h`,
  `#pragma pack(1)`, 26 байт/точку: `x,y,z,intensity` float32 (offset
  0/4/8/12) + `tag,line` uint8 (offset 16/17) + `timestamp` float64 (offset
  18)), публикует на `livox/lidar` с `frame_id="livox"`. `intensity` в
  этом сообщении = `reflectivity` (uint8 0..255) как есть, без пересчёта —
  формулу масштабирования реального `pub_handler.cpp` не искали (не
  требовалось для CustomMsg, а глубже не закапывались)
- `frame_id` на CustomMsg **уже верный без дополнительных танцев** с
  `<frame_name>` (в отличие от `libgazebo_ros_imu_sensor.so` у обоих IMU) —
  этот плагин берёт `frame_id` из ИМЕНИ САМОГО СЕНСОРА (`<sensor name="livox">`
  → `raySensor->Name()`), а не из линка, поэтому проблема fixed-joint-lumping
  его не касается
  - ⚠️⚠️ **но сам TF-фрейм `livox` этим не создаётся** — имя фрейма в
    сообщении верное, а транформа для него не существовало вообще (в
    `urdf/mast.urdf.xacro` был только `lidar_mount_link`). На реальном
    роботе `livox` — отдельный явный `static_transform_publisher` из
    `mid360.launch.py`, а не часть URDF-дерева. Без этого RViz не мог
    зарезолвить точки НИ В КАКОМ Fixed Frame (`Message Filter dropping
    message... queue is full` не переставая — нашли только через живой
    тест с RViz, не через компиляцию/логи плагина). Фикс — добавлен
    безразмерный `<link name="livox"/>` нулевым `<joint>` от
    `lidar_mount_link` (сам `lidar_mount_link` уже верно сориентирован,
    см. IMU-блок — просто дать этой позиции ещё и правильное имя фрейма)
- Живьём подтверждено (`ros2 topic echo`, ручная распаковка байт `struct.
  unpack_from('<ffffBBd', ...)`): точки на скан, дистанции от 0 до ~165м
  (среднее ~1.7м — в основном попадания в собственный корпус/платформу
  робота и пол, мир для теста пустой), reflectivity везде 0 (правильно —
  в пустом мире нет объектов с `laser_retro`, ничего другого там и не
  должно отражаться; **подтверждено активным тестом** — заспавнили в мир
  бокс с `<laser_retro>200</laser_retro>`, в облаке тут же появилось 607
  точек с `intensity=200` в правильном направлении — весь конвейер SDF
  laser_retro → CustomMsg.reflectivity → `livox_lidar_bridge.py` →
  PointCloud2.intensity рабочий end-to-end, "всё красное" в пустом мире —
  корректное поведение, не баг)
- ⚠️⚠️ **`<publish_rate>` у плагина вообще НЕ парсится из SDF** (не просто
  "не делает то, что заявлено" — грепом по исходнику подтверждено: из тегов
  `<samples>`/`<downsample>` читаются оба, `<publish_rate>` не читается
  нигде вообще). Реальная частота публикации определяется исключительно
  тем, что физически успевает посчитаться при заданном `<update_rate>` —
  из той же серии нерабочих SDF-тегов, что и `<command_topic>` у diff_drive.
  Патчить не стали (третий/четвёртый патч в этот плагин за сессию — решили
  подбирать `lidar_samples` эмпирически под фактическую производительность,
  а не чинить ещё один слой)
- **`lidar_samples` подобран эмпирически под реальные данные и
  производительность**: в `data/rosbag2_..._static_1m` (реальная запись с
  этапа квалификации) — `/livox/lidar` реально даёт **~20000 точек/сообщение
  на ~8.5Гц** (совпадает с `publish_freq=10.0` из `mid360.launch.py`),
  intensity размазана по всему диапазону 0..255 (не только 0/255 —
  34% точек ровно 0, остальное — плавное распределение, в основном 1-30).
  Раскладка полей сообщения (`offset`/`datatype` для x,y,z,intensity,tag,
  line,timestamp) сверена побайтово с нашей — совпадает 1-в-1, реальное
  подтверждение того, что байтовый макет из `lddc.cpp` был реконструирован
  верно. Замерили `lidar_samples` эмпирически (`ros2 topic hz` +
  `/clock` vs wall-time = real-time factor): на 1500 — ~30Гц; на 10000 —
  ~5.8-6Гц, real-time factor ~0.68, ~58500 точек/сек суммарно; на 20000 —
  ~2.7Гц, ~54000 точек/сек (МЕНЬШЕ, чем на 10000 — деградация
  непропорциональная, плюс ~17с на первый скан при старте). Остановились
  на **10000** — лучший суммарный поток данных из протестированных, вдвое
  меньше точек на скан, чем у реального робота, но не из экономии, а
  потому что у этого плагина 20000 объективно не имеет смысла при текущей
  производительности
- ⚠️⚠️⚠️ **Самая серьёзная находка: скан вообще не обновлялся —
  каждый вызов выбирал одни и те же строки CSV, точки всегда были в
  одних и тех же местах при любом запуске** (задержка ниже — реальная,
  но отдельная, второстепенная проблема; эта была первопричиной того,
  что "облако не обновляется"). В `livox_points_plugin.cpp`,
  `InitializeRays()` (вызывается каждый кадр из `OnNewLaserScans()`):
  `index = (r * stride) % maxPointSize` — чистая функция от `r` и
  констант, без единого завязанного на время/кадр слагаемого. `SetPoints()`
  на лучах реально перевызывается каждый кадр (сам механизм рабочий,
  не заглушка), просто ВСЕГДА переустанавливает лучи В ТЕ ЖЕ САМЫЕ
  направления. `currStartIndex` (поле `int64_t currStartIndex = 0;` в
  `livox_points_plugin.h`, под "sliding window" механизм нерепиты-скана)
  был объявлен, упомянут в комментарии над функцией — и нигде фактически
  не использовался. Тот же почерк незаконченного рефакторинга, что и с
  CustomMsg (см. выше) — автор форка начал и бросил.
  **Фикс**: `index = (r * stride + currStartIndex) % maxPointSize`,
  плюс `currStartIndex = (currStartIndex + ray_count) % maxPointSize;`
  в конце функции. Проверено вживую: координаты первой точки в
  последовательных сообщениях `_raw/livox_lidar` теперь РАЗНЫЕ (были бы
  идентичны при старой формуле); за 10с работы через `livox/lidar`
  насчитано ~61000 уникальных (округлённых) координат точек против
  жёсткого потолка ~1500 до фикса
- ⚠️⚠️ **Облако в RViz визуально "отставало" от модели при движении и
  "нагоняло" при остановке** — не баг замороженного буфера (данные
  реально свежие каждый раз, `header.stamp` растёт), а настоящая, реально
  измеренная задержка. Причина в двух слоях:
  1. У самого плагина (`_raw/livox_lidar`) базовая задержка ~0.15-0.3с
     (похоже на особенность накопления скана перед публикацией, не
     трогали — глубже в сам плагин не лезли)
  2. `scripts/livox_lidar_bridge.py` добавлял СВЕРХУ ещё и РАСТУЩУЮ
     задержку: поточечный `struct.pack_into` в Python-цикле на ~1500
     точек не успевал за реальной частотой потока (~30-33Гц, см. пункт
     выше про `publish_rate`) — копился нарастающий бэклог. Внешне это
     выглядело именно как "отставание, догоняющее при остановке"
     (задержанные точки транслируются в текущий Fixed Frame по СТАРОЙ
     позиции робота — разрыв пропорционален скорости × лагу, при
     остановке разрыв естественно исчезает, хотя сам лаг никуда не делся).
     В логе RViz это же самое — `Message Filter dropping message...
     timestamp is earlier than all the data in the transform cache`.
     **Фикс**: переписали упаковку на `numpy` structured array
     (векторизованное присвоение по полям вместо 1500 отдельных вызовов
     `struct.pack_into`) — живым тестом (20с непрерывного движения с
     поворотами) подтверждено: задержка держится в узком диапазоне
     ~0.16-0.36с и НЕ растёт (первые/последние 10 замеров — 0.305с vs
     0.241с, то есть стабильна или даже падает). "earlier than cache"
     после фикса больше не повторяется — только один раз на самом старте
     (t=0.2с, пока у RViz ещё пустой буфер TF), это нормальный переходный
     процесс, не постоянная проблема

⚠️ Лог при старте один раз печатает `[ERROR] convertDataToRotateInfo data
size is 800000!` — не баг, просто автор форка оставил информационный принт
("вот сколько строк CSV загрузил") на уровне `RCLCPP_ERROR` вместо `INFO`.
Не повторяется, на работу не влияет, не патчили (косметика чужого кода)

**Для человека, который делает макет поля**: отражательная способность в
Gazebo задаётся через `<collision><laser_retro>N</laser_retro></collision>`
в SDF, а НЕ визуальной текстурой/материалом — лидар её не видит.

## Gazebo-плагины двойника — принцип и статус

**Ключевой принцип**: топики, типы сообщений и имена фреймов у двойника
должны совпадать с тем, что публикует/принимает реальный драйвер
(`kobuki_node` для базы, `livox_ros_driver2` для лидара) — тогда командный
код (Nav2, детекция, валидация маркеров и т.п.) переносится на реального
робота без переписывания топиков/типов, только сменой источника данных.
Несовпадение форматов — это не мелочь, а то, что ломает перенос в последний
момент на самом полигоне.

- **Diff drive + энкодеры (готово, проверено вживую в Gazebo)**:
  `differential_drive_controller` (`libgazebo_ros_diff_drive.so`) +
  отдельный `gazebo_ros_joint_state_publisher`
  (`libgazebo_ros_joint_state_publisher.so`) в `urdf/kobuki_gazebo.urdf.xacro`.
  Тестовый запуск: `ros2 launch hsl_description gazebo.launch.py` (новый
  launch-файл, спавнит модель в Gazebo — отдельно от
  `robot_description.launch.py`, который только для RViz-превью без физики).
  Сверено с `kobuki_node/src/kobuki_ros.cpp` и
  `kobuki_node/config/kobuki_node_params.yaml`:
  - команда скорости: топик **`commands/velocity`** (НЕ `cmd_vel` — так было
    изначально в апстримном плагине kobuki_description, поправлено),
    `geometry_msgs/Twist` — тип совпадал изначально, поправлено только имя топика
  - одометрия: топик `odom`, `nav_msgs/Odometry`, `odom_frame=odom`,
    `robot_base_frame=base_link` — совпадало уже в апстримном плагине
  - ⚠️⚠️ **`base_footprint` в TF-дереве фактически "сирота"** — важно
    для будущего Nav2 (задача #4 в команде). Причина: `robot_base_frame=
    base_link` (сделано специально, совпадает с реальным `kobuki_node_params.
    yaml: base_frame: base_link`) означает, что `differential_drive_controller`
    публикует `odom -> base_link` НАПРЯМУЮ, в то время как
    `robot_state_publisher` (из URDF) публикует `base_footprint -> base_link`.
    У `tf2` фрейм может иметь только ОДНОГО родителя — при конфликте
    побеждает более свежее сообщение, а `odom -> base_link` переиздаётся
    непрерывно (в отличие от статического `base_footprint -> base_link`,
    отданного один раз), поэтому `base_footprint` в итоге не имеет пути ни
    к чему. Проверено вживую: `tf2_echo odom livox` резолвится, `tf2_echo
    base_footprint livox` — `"Tf has two or more unconnected trees"`.
    Из-за этого `rviz/gazebo.rviz` использует `Fixed Frame: odom`, НЕ
    `base_footprint` (иначе RViz ничего не отрисует — почти взяли
    `base_footprint` при отладке невидимого облака точек, эмпирическая
    проверка через `tf2_echo` показала обратное тому, что казалось логичным
    на бумаге). Если Nav2 потребует именно `base_footprint` как
    `robot_base_frame` (стандартная практика для costmap) — придётся либо
    отступить от точного совпадения с `kobuki_node_params.yaml` и завести
    `robot_base_frame=base_footprint` на плагине, либо городить отдельный
    релей-узел; не решено, чисто фиксация находки на будущее
  - joint states (энкодеры): `joint_states`, `sensor_msgs/JointState`, имена
    joint'ов `wheel_left_joint`/`wheel_right_joint` совпадают с
    `wheel_left_joint_name`/`wheel_right_joint_name` из `kobuki_node_params.yaml`
  - `sensors/core` (сырые тики энкодеров, готово): реальный драйвер вдобавок
    публикует `kobuki_ros_interfaces/msg/SensorState` — кастомный тип,
    штатный Gazebo-плагин его в принципе произвести не может. Мост
    `scripts/wheel_encoders_bridge.py` (rclpy-нода, установлена через
    `install(PROGRAMS ...)` в `CMakeLists.txt`, запускается вместе с
    `gazebo.launch.py`) слушает `joint_states`, считает "сырые" тики через
    реальную константу `tick_to_rad = 0.002436916871363930187454`
    (`kobuki_core/src/driver/diff_drive.cpp`, **не** число тиков/оборот "на
    глаз" — у разных энкодеров разное) и публикует `left_encoder`/
    `right_encoder` (`uint16`, накопительно, **переполнение на 65536** —
    так же ведёт себя реальное железо) в `sensors/core` на 50Гц (совпадает
    с `SensorState.msg`: "transmitted at 50Hz"). Проверено вживую: тики
    растут монотонно при движении. Требует пакет `kobuki_ros_interfaces`
    (см. структуру workspace выше — симлинк, собран отдельно).
    ⚠️ **При повороте на месте один энкодер растёт, другой уходит в
    переполнение и "считает вниз"** (например `left_encoder: 63208` вместо
    маленького числа) — это НЕ баг моста, а ожидаемая физика: при повороте
    одно колесо крутится вперёд, другое назад, сырые инкрементальные
    энкодеры это честно отражают. Подтверждено кодом реального драйвера:
    `diff_drive.cpp` явно обрабатывает именно такой случай через
    `(short)((curr_tick - last_tick) & 0xffff)`. При прямом движении оба
    энкодера растут синхронно в одну сторону — тоже проверено.
    ⚠️ Остальные поля `SensorState` (бампер, cliff, wheel_drop, PWM,
    батарея, зарядка, buttons, digital/analog input) **не заполнены**
    (нули/пустые массивы) — под них пока нет Gazebo-плагинов, отдающих эти
    данные в ROS. Если код команды их читает — это не готово
  - ⚠️⚠️ **два реальных бага плагинов этой версии (Gazebo 11 Classic +
    `gazebo_plugins` Humble), найдены только живым тестом, а не по докстрингам
    заголовков — доверять последним нельзя**:
    1. У `libgazebo_ros_diff_drive.so` плоские теги `<command_topic>`/
       `<odometry_topic>` **не работают**, несмотря на то, что упомянуты в
       `gazebo_ros_diff_drive.hpp` — топик молча остаётся дефолтным
       (`cmd_vel`/`odom`). Переименование топика — только через
       `<ros><remapping>cmd_vel:=commands/velocity</remapping></ros>`
       (синтаксис сверен с официальным демо-миром пакета:
       `gazebo_ros_diff_drive_demo.world`)
    2. Тег `<publish_wheel_joint_state>` у того же плагина заводит топик
       `joint_states` с правильными именами joint'ов, но **не обновляет
       сами значения** (проверено: робот проехал ~0.7м по `/odom`, а
       `/joint_states` всё это время стоял на `0.0/0.0`). Рабочее решение —
       отдельный плагин `gazebo_ros_joint_state_publisher` с явным списком
       `<joint_name>` (сверено с `gazebo_ros_joint_state_publisher_demo.world`,
       после этого `position`/`velocity` реально меняются)
- **IMU 6-осевой Livox (готово, проверено вживую)**: IMU **внутри Livox
  MID-360** (ICM-40609) — НЕ путать с гироскопом самой базы kobuki
  (`gyro_link`, отдельный физический сенсор, см. выше). Плагин
  `libgazebo_ros_imu_sensor.so` на `lidar_mount_link` в `mast.urdf.xacro`
  публикует "сырой" физически честный IMU на скрытый `_raw/livox_imu`,
  `scripts/livox_imu_bridge.py` переформатирует в `livox/imu` под точную
  семантику реального `livox_ros_driver2` (сверено с исходником
  `src/lddc.cpp::InitImuMsg`, не по памяти/докам):
  - `orientation` реальный драйвер вообще не заполняет (у ICM-40609 нет
    магнетометра) — у нас тоже остаётся identity-кватернионом по умолчанию
    (ROS2 IDL default `w=1`, не "нулевым" — это тоже проверено, не какая-то
    догадка)
  - `linear_acceleration` в единицах **"g", БЕЗ домножения на 9.81**
    (см. известный баг реального драйвера, issue #157, уже описан выше) —
    мост намеренно делает то же самое (`/9.81` от честного Gazebo-ускорения
    в м/с²), это не "исправлено", а воспроизведено, чтобы код команды,
    уже учитывающий этот баг, поведением не отличался от реального робота
  - `frame_id` жёстко `"livox_frame"` (`lddc.cpp:481`), как и у реального
    драйвера — воспроизведено намеренно, а не то, что "правильнее" (в TF
    дереве фрейм называется иначе, это тот же известный рассинхрон, что
    описан выше в секции про сенсоры)
  - **`lidar_mount_joint` теперь развёрнут по-настоящему**: `rpy` в
    `mast.urdf.xacro` поправлен с плейсхолдера `0 0 0` на реальный
    `rpy=0 π π/2` (из static TF `mid360.launch.py`, см. вывод формулы выше
    в этом же файле) — это не декоративная деталь: живьём подтверждено, что
    без неё показания IMU были бы в развёрнутых осях. С фиксом в покое
    `linear_acceleration.z ≈ -1.0g` (не +1.0 — сенсор физически перевёрнут),
    при команде `angular.z=0.5` гироскоп репортит `≈ -0.5` (тоже из-за
    переворота, тоже верно) — обе проверки живые, не расчёт на бумаге.
    Высота (z) крепления всё ещё placeholder, ориентации это не касается
  - частота публикации ~200Гц — сверено вживую (`ros2 topic hz`),
    совпадает с реальным сенсором
  - те же капризы `<frame_name>` в двух местах (`<sensor>` и `<ros>`), что
    и у гироскопа kobuki — сам fixed-joint-chain (`platform_link ->
    lidar_mount_link`) точно так же требует этого
- **Лидар (готово, подключён и проверен вживую)**: см. подробности,
  найденные проблемы форка и результаты живого теста в секции «Симуляция
  лидара» выше — `livox/lidar` (`sensor_msgs/PointCloud2`, `frame_id="livox"`,
  intensity сохранена через `scripts/livox_lidar_bridge.py`)
- **Не проверено на соответствие драйверу** (плагины уже есть в
  `kobuki_gazebo.urdf.xacro`, унаследованы из апстрима, но топики/форматы
  под реальный `sensors/core` не сверялись): бампер (`contact`-сенсор на
  `base_link`) и 3 cliff-датчика (`ray`-сенсоры) — тоже часть `SensorState.msg`
  на стороне реального драйвера
- **IMU гироскопа kobuki (`gyro_link`, готово, включая семантику, проверено
  вживую)**: `libgazebo_ros_imu_sensor.so` на `gyro_link` в
  `kobuki_gazebo.urdf.xacro` публикует "сырой", физически честный IMU (все
  3 оси) на СКРЫТЫЙ топик `_raw/gyro_imu` (`<ros><remapping>~/out:=_raw/gyro_imu
  </remapping></ros>`, не для прямого использования командой). Обрезку до
  формата реального драйвера делает `scripts/gyro_imu_bridge.py`
  (rclpy-мост, по образцу `wheel_encoders_bridge.py`), который и публикует
  итоговый `sensors/imu_data`, подписан на всё в `gazebo.launch.py`.
  - ⚠️⚠️ **`frame_id` у сырого сенсора был неверным (`base_footprint` вместо
    `gyro_link`)** — `base_footprint → base_link → gyro_link` соединены
    fixed-joint'ами, URDF→SDF конвертер по умолчанию склеивает их в один
    линк (имя достаётся корневому `base_footprint`). Фикс —
    `<frame_name>gyro_link</frame_name>` (реальный, задокументированный
    механизм `gazebo_ros::SensorFrameID()` из `gazebo_ros/utils.hpp`, НЕ
    придуманный parameter, но мост всё равно жёстко перезаписывает
    `frame_id="gyro_link"` сам, так что для итогового топика это не
    критично). Матчасть капризная: по отдельности ни `<frame_name>` на
    уровне `<sensor>`, ни внутри `<plugin>`, ни внутри `<ros>` не сработали —
    заработало только когда он одновременно и на уровне `<sensor>`, и
    внутри `<ros>` у плагина. Проверено живым A/B тестом (5+ прогонов), не
    выводится ни из какой доки
  - **Семантика (по явному запросу — обрезано под реальный драйвер, а не
    оставлено "богаче")**: `kobuki_ros.cpp::publishInertia()` заполняет
    только yaw в `orientation` (roll/pitch всегда 0) и `angular_velocity.z`
    (x/y всегда 0), `linear_acceleration` не публикует вообще (у гироскопа
    его физически нет), covariance = `DBL_MAX` на неиспользуемых осях,
    `0.05` на используемой (сигнал "не доверяй" для `robot_pose_ekf`-подобных
    консьюмеров). `gyro_imu_bridge.py` воспроизводит это один в один: yaw
    достаётся из полного физического кватерниона (`atan2`), пересобирается
    в roll=pitch=0 кватернион, `linear_acceleration` не трогается (остаётся
    нулевым, как и у реального драйвера), covariance выставлена так же.
    Живьём подтверждено: `angular_velocity.z ≈ 0.5` устойчиво при команде
    `angular.z=0.5`, x/y всегда 0, `linear_acceleration` всегда 0

## Регламент — конспект (полный текст: `hsl25-master/docs/Очный - HSL25 v021025.pdf`)

- Задачи: SLAM, планирование движения в динамической среде, идентификация/
  локализация объектов и роботов
- Полигон: лабиринт из модулей ~1×1м + статические препятствия (ширина/длина
  от 0.1м, высота от 0.15м, непрозрачные, незеркальные), конфигурация
  сообщается в первый день, во время соревнований может измениться на ±1 панель
  на площади 2×3м
- **Маркеры трёх типов — X, T, O — различаются ФОРМОЙ, не цветом** (у лидара
  нет цветового канала). Все из светоотражающего материала на фоне с меньшей
  отражательной способностью. T и O — баллы, X и ложные срабатывания — штраф
- Обнаружение засчитывается: робот ≤1.5м от маркера, ≤45° от нормали маркера,
  прямая видимость (нет препятствий), ось X робота направлена на маркер
  непрерывно ≥5 секунд
- На выступление 20 минут: 5 мин на запуск ПО + 15 мин на прохождение. 2
  бесплатных рестарта (обнуляют баллы/штрафы). Запрещено во время доп.
  подготовки фиксировать в коде информацию об уже увиденных особенностях
  полигона
- Столкновения: слабое (подвижное препятствие сдвинулось ≤0.1м) — штраф;
  сильное — на усмотрение судей, можно рестартовать
- **Запрещено**: любая доп. сенсорика, доп. сетевое оборудование, апгрейд
  производительности бортового ПК — оборудование у всех команд одинаковое



Bag-файлы с этапа квалификации (робот стоит на месте): полезны для отладки
**детекции маркеров** (плотное статичное облако накапливается благодаря
неповторяющемуся скану даже без движения), малополезны для **SLAM**
(нет связки движение+лидар)
